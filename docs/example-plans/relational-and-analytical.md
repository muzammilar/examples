# Relational databases, analytical engines and wide-column stores

These are proposed experiments. Start with one checkbox. Existing [PostgreSQL](../../postgres/), [MySQL](../../mysql/) and [StarRocks](../../starrocks/) results identify the baselines available for reuse. Use the [lab and evidence rules](../../AGENTS.md) for every case.

## PostgreSQL and its extensions

- [ ] **PostgreSQL single-node — order corrections.** Use the current stable major for a plain heap baseline. Replay indexed order updates alongside a historical scan, then crash during a checkpoint. Verify every committed order and its customer total after WAL replay. Save plans and physical I/O for the scan separately from OLTP. [Supported versions](https://www.postgresql.org/support/versioning/)
- [ ] **Patroni with etcd — promotion eligibility follow-up.** Extend the [existing tested HA group](../../postgres/pgdog-docker-compose-cluster/) with one primary and two standbys. Replay the same orders under asynchronous and strict synchronous settings. Isolate the primary, then return it. Check which node accepts writes and diff externally acknowledged rows by timeline. Record observed async loss and time strict mode spent waiting. [Patroni replication modes](https://patroni.readthedocs.io/en/latest/replication_modes.html)
- [ ] **CloudNativePG — recovery to a transaction boundary.** In a private kind cluster, archive WAL and a base backup through the supported Barman Cloud plugin to a lab-owned S3 endpoint. Insert marked orders before and after a named recovery point, switch primary, then restore a separate cluster. Verify the exact order set at the selected boundary. [Barman Cloud plugin](https://cloudnative-pg.io/plugin-barman-cloud/) · [Recovery](https://cloudnative-pg.io/docs/devel/recovery/)
- [ ] **Citus — interrupted tenant relocation.** Extend the existing three-worker-group lab. Interrupt a shard move during updates to colocated orders and line items, then complete or reverse it using the supported procedure. Check native placement, tenant-local query results and order totals through the coordinator and on the owning workers. [Existing cluster](../../postgres/citus-docker-compose-cluster/) · [Distribution columns and colocation](https://docs.citusdata.com/en/stable/sharding/data_modeling.html)
- [ ] **PgDog — live resharding.** Extend the existing customer-sharding example with old and new layouts, leaving the pooling example independent. Interrupt the copy before cutover, resume from the supported point and compare per-customer receipts on each owner before retiring the original layout. [Existing shard test](../../postgres/customer-sharding/) · [Resharding procedure](https://docs.pgdog.dev/features/sharding/resharding/)
- [ ] **Multigres — tenant connections through primary loss.** Start with one table group, a gateway, poolers and a supported replicated PostgreSQL deployment. Fail the primary with long-lived sessions and fresh connections active. Reconcile committed order IDs and role transitions. Add a multi-shard cell only when a stable self-hosted release exposes working routing and migration. [Project status](https://github.com/multigres/multigres) · [Architecture](https://multigres.com/docs/architecture)
- [ ] **PgBouncer — connection bursts with session state.** Compare transaction and session pooling against the existing PgDog burst on the same backend connection budget. Disconnect one client inside a transaction and reuse a server connection across two tenants. Check rollback, tenant isolation, accepted clients and wait time. [Pooling compatibility](https://www.pgbouncer.org/features.html) · [Existing PgDog workload](../../postgres/pgdog-docker-compose-cluster/)
- [ ] **ReadySet — freshness of a cached order dashboard.** Exercise one supported parameterized query, an uncached control and authoritative direct reads. Stop its replication feed while customers change orders, reconnect and compare each result to source versions. Record fallback routing, visibility delay and catch-up. [ReadySet design and supported upstreams](https://github.com/readysettech/readyset)
- [ ] **ParadeDB — search while inventory changes.** In PostgreSQL, search a labelled catalogue by text score plus tenant and stock filters. Cancel a product update, commit another and reopen after a crash. Compare eligible IDs and deterministic tie-broken ordering against a fixed relevance fixture. Include PostgreSQL full-text search as a separate ranking baseline. [pg_search](https://github.com/paradedb/paradedb)
- [ ] **OrioleDB — long snapshots under update churn.** Build against the exact upstream PostgreSQL patchset required by the chosen OrioleDB release. Hold a reader snapshot across repeated updates, then crash during checkpointing. Compare pre-crash snapshot contents and post-reopen latest rows with the same transactions on PostgreSQL heap. [Required PostgreSQL patchset and build checks](https://github.com/orioledb/orioledb/blob/main/README.md)
- [ ] **Apache Cloudberry — skewed joins and segment recovery.** Use a coordinator and mirrored segments. Compare a customer-colocated join with a deliberately skewed distribution, kill one primary segment during live queries, and recover its mirror. Check per-customer sums, data movement in the plan and restored redundancy. [Segment recovery](https://cloudberry.apache.org/docs/sys-admin/high-availability/recover-from-segment-failures/)
- [ ] **openGauss — memory-optimized inventory.** If the selected image includes MOT, compare identical reservations on MOT and ordinary tables under the same durable commit policy. Crash with acknowledged updates after a checkpoint, then check remaining quantities and every reservation. Capture checkpoint and redo storage separately. [MOT memory and storage](https://docs.opengauss.org/en/docs/latest/database_administration_guide/mot_memory_and_storage_planning.html)
- [ ] **pg_duckdb — analytical reads inside PostgreSQL.** Compare a scan and join over PostgreSQL and local Parquet through DuckDB with a native SQL control. Include upstream's negative transaction case that writes to PostgreSQL and DuckDB tables together. Check that rejection leaves neither half visible. [Transaction restrictions](https://github.com/duckdb/pg_duckdb/blob/main/docs/transactions.md)
- [ ] **pg_mooncake — freshness of an Iceberg columnstore mirror.** Stream inserts, updates and deletes from a PostgreSQL row table into its mirror. Interrupt replication with source writes active. At a known final commit compare full primary-key sets and bodies, then report the time to convergence and WAL retained during the outage. Use the project's compatible extension bundle. [Mirror setup and replication](https://github.com/Mooncake-Labs/pg_mooncake/blob/main/README.md)
- [ ] **AlloyDB Omni — columnar acceleration on a mixed workload.** Use the local container edition. Populate selected columns, interleave order updates and scans, and compare eligible plans and exact totals before and after disabling the columnar engine. Restart and inspect residency and repopulation time. [Columnar engine configuration](https://docs.cloud.google.com/alloydb/omni/containers/current/docs/columnar-engine/configure)
- [ ] **Neon and PostgreSQL comparison — remote-page reads versus shard routing.** Repeat a tenant-local lookup and a global aggregate across plain PostgreSQL, Neon, Citus, sharded PgDog and eligible Multigres configurations. Verify the same bodies at a fixed watermark. Isolate Neon compute-cache refill as a separate case and report shard ownership only for systems that distribute the writes. [Existing Neon lab](../../postgres/neon/) · [Neon architecture](https://neon.com/docs/introduction/architecture-overview)

## MySQL and its ecosystem

- [ ] **MySQL single-node — stock reservation baseline.** InnoDB transactions reserve an item and write a receipt under a unique request ID. Repeat IDs, introduce a deadlock, then crash and reopen. Verify no negative stock, each receipt and the exact committed delta. Pin a supported stable server that matches comparison clients. [InnoDB transactions](https://dev.mysql.com/doc/refman/8.4/en/innodb-transaction-model.html)
- [ ] **InnoDB Cluster — catch-up on primary change.** Use three Group Replication members and MySQL Router. Build an apply backlog, stop the primary and issue reads/writes via Router during election. Compare last acknowledged versions with reads on the new primary under declared consistency settings. [InnoDB Cluster](https://dev.mysql.com/doc/mysql-shell/8.4/en/mysql-innodb-cluster.html) · [Failover consistency](https://dev.mysql.com/doc/refman/8.4/en/group-replication-configuring-consistency-guarantees.html)
- [ ] **MySQL Operator — declarative recovery on kind.** Use Oracle's InnoDB Cluster operator for this design. Drain a worker holding a secondary, restore redundancy, then interrupt the operator while replacing another pod. Verify native group membership, Router write recovery and receipts. A Percona XtraDB Cluster variant requires its own Galera contract. [MySQL Operator manual](https://dev.mysql.com/doc/mysql-operator/en/)
- [ ] **MariaDB Galera — certification conflicts.** Update hot inventory through two writable nodes in a three-node primary component. Partition one node, continue reservations where permitted and rejoin it. Compare certification failures, successful retries and final quantities across nodes. Capture incremental versus full state transfer. [Galera replication](https://mariadb.com/docs/galera-cluster/about-galera-replication)
- [ ] **ProxySQL — replica lag and read routing.** Use writer and reader hostgroups in front of replicated MySQL. Record the selected backend for an immediate receipt read and a historical dashboard read. Delay one replica and exercise a connection pool through promotion. Verify session guarantees and disqualification of lagged replicas against the configured rules. [Read/write split](https://proxysql.com/documentation/proxysql-read-write-split-howto/)
- [ ] **Vitess — online Reshard and operator operation.** Extend the existing fixed-shard lab with a VReplication copy, VDiff and read/write traffic switches. Interrupt a target tablet, then compare keyrange placement and full receipts before source retirement. In a separate kind deployment, interrupt operator reconciliation during a tablet-count change and verify actual serving membership. [Current fixed topology](../../mysql/customer-sharding/) · [Upstream cutover example](https://github.com/vitessio/vitess/blob/main/examples/compose/README.md) · [Operator](https://github.com/planetscale/vitess-operator)
- [ ] **ShardingSphere-Proxy — customer routing and distributed transfer.** Route tenant-local orders across three database shards, then transfer a balance across two using a supported XA configuration. Interrupt a participant around commit and run native recovery. Reconcile the two legs, account totals and physical ownership. Repeat the portable workload with the PostgreSQL backend separately. [ShardingSphere](https://github.com/apache/shardingsphere)
- [ ] **PolarDB-X — secondary-index consistency during recovery.** On an operator-managed cluster, look up the same order by partition key and global secondary key while writers change its indexed status. Stop a compute node and then, separately, a data-node leader. Compare both read paths after recovery and check the partition map. [Architecture](https://github.com/polardb/polardbx) · [Operator](https://github.com/polardb/polardbx-operator)
- [ ] **MatrixOne — analytical visibility of transaction commits.** Use compute, transaction and log services with an isolated object store. Replay order corrections and have a separate reader query a fixed committed watermark. Restart a compute node, then interrupt object storage separately. Verify transaction bodies and grouped totals after reconnection. [LogService architecture](https://docs.matrixorigin.cn/mo/en/v26.4.1.4/MatrixOne/Overview/architecture/architecture-logservice.html) · [Engine](https://github.com/matrixorigin/matrixone)
- [ ] **Customer-sharding comparison — routing cost and failure scope.** Reuse the order history for plain MySQL, Vitess, ShardingSphere, PolarDB-X, NDB, RonDB and TiDB. Compare customer-local transactions and cross-customer aggregates, including the number of partitions touched and impact of one node loss. Use common operations and equal durability for a ranking. Link the PgDog/Citus results for the cross-protocol comparison. [MySQL cases](../../mysql/) · [RonDB](../../rondb/) · [TiDB](../../tidb/)
- [ ] **NDB/RonDB — node-group expansion with live quotas.** Extend the existing NDB subscriber test and give RonDB the same versioned profile oracle. Insert a node group, explicitly redistribute partitions where required and stop one copy after movement. Verify every quota debit and native fragment placement against the before/after maps. [NDB node groups](https://dev.mysql.com/doc/refman/9.7/en/mysql-cluster-nodes-groups.html) · [Existing NDB lab and failed disk-full run](../../mysql/ndb-cluster-docker-compose-cluster/)

## In-memory OLTP

- [ ] **Volt Active Data — partition-local authorization.** With a compatible local Developer Edition, authorize prepaid debits through a deterministic partitioned SQL procedure. Compare same-account and cross-partition work. If the edition permits K-safety, stop a replica under load and verify each debit, balance and declared recovery point. [Local distribution](https://developers.voltactivedata.com/get-started) · [K-safety](https://docs.voltdb.com/AdminGuide/HostConfigDBOpts.php)
- [ ] **SpacetimeDB — multiplayer state after reconnect.** On a local standalone server, two Rust game clients submit competing moves for one item while a third subscribes to the visible room. Disconnect the subscriber, crash the server and reconnect. Compare its rebuilt view with committed reducer outcomes and full state at a known version. Track event replay separately if available. [Self-hosting](https://spacetimedb.com/docs/how-to/deploy/self-hosting/) · [Subscriptions](https://spacetimedb.com/docs/clients/subscriptions/)

## Real-time OLAP

- [ ] **StarRocks — shared-data compute replacement.** The FE/BE deployments and mutable-orders comparison already exist. Use FE/CN shared-data mode with a local object store, retire a warm compute node under traffic and add an empty one. Verify exact order versions and join totals during refill, then test object-store loss separately. [Existing results](../../starrocks/) · [Architecture](https://docs.starrocks.io/docs/introduction/Architecture/)
- [ ] **Apache Doris — out-of-order inventory updates.** Feed duplicate, stale and deleted orders to a Unique Key table with an explicit sequence column. Lose one tablet replica during reads, rebuild it and check the latest version for each key as well as regional sums. In a second deployment test compute-cache refill with shared storage and its metadata dependencies. [Update ordering](https://doris.apache.org/docs/4.x/data-operate/update/unique-update-concurrent-control/) · [Storage separation](https://doris.apache.org/docs/3.x/compute-storage-decoupled/overview/)
- [ ] **Apache Pinot — live delivery status and a separate event dashboard.** Key Kafka partitions by order ID and use explicit versions for the upsert table. Restart a server during segment handoff and check each latest status. Use a separate append-only table for the star-tree dashboard and compare bucketed event sums with the input log. [Upsert limitations](https://docs.pinot.apache.org/build-with-pinot/ingestion/upsert-dedup/upsert) · [Table configuration validator](https://github.com/apache/pinot/blob/master/pinot-segment-local/src/main/java/org/apache/pinot/segment/local/utils/TableConfigUtils.java)
- [ ] **Apache Druid — event rollup through segment handoff.** Send the same immutable Kafka events to raw and rolled-up datasources. Restart an indexing task across handoff, then evict a historical server's local segment copy. Compare event-ID coverage on the raw path and time-bucket sums on both paths after retrieval from local deep storage. [Rollup semantics](https://druid.apache.org/docs/latest/ingestion/rollup/) · [Deep storage](https://druid.apache.org/docs/latest/design/deep-storage/)
- [ ] **Databend — rebuilding compute over object storage.** Load sales into Fuse tables over lab-owned storage. Capture a snapshot, append a correction and replace the query process with an empty cache while keeping metadata and objects. Check old and latest reports at their respective snapshots. Measure metadata availability and object-store failure separately. [Databend engine and deployment](https://github.com/databendlabs/databend)
- [ ] **Firebolt Core — selective dashboard queries.** Run Core locally on a versioned clickstream fixture, comparing selective filters and broad aggregates with the same input on StarRocks. Stop and recreate the query process with its documented storage preserved. Check complete tenant totals and separate cold reopen from warm latency. [Core distribution and local storage options](https://github.com/firebolt-db/firebolt-core)
- [ ] **Exasol — bounded local Docker evaluation.** Choose the vendor's Docker evaluation image within its raw-data allowance, subject to local architecture and runtime prerequisites. Load a skewed fact/dimension model, compare join results with a reference and verify a retained-volume reopen. Exasol Personal is a separate Launcher distribution. [Edition and Docker limits](https://docs.exasol.com/db/latest/get_started/exasol_editions.htm)
- [ ] **Vertica — projection locality under a local trial.** Gate on a valid current trial and permitted topology. In a local Enterprise Mode cluster declare buddy projections and K-safety for a tenant sales table. Lose one node and verify exact aggregates and projection coverage after recovery. Skip cluster claims when the licensed shape cannot exercise them. [Current evaluation policy](https://docs.rocketsoftware.com/bundle/vertica_26.2/page/getting-started/community-edition-ce.html)
- [ ] **CrateDB — relocation during industrial telemetry queries.** Use three primary shards with two replicas each, separate tenant skew from time partitioning and inject a node outage. Check time/tenant totals against the input and inspect every shard's placement when redundancy returns. Compare common filters with GreptimeDB and text queries separately with Elasticsearch. [Shards, replicas and active-shard requirements](https://cratedb.com/docs/crate/reference/en/latest/sql/statements/create-table.html)
- [ ] **HeavyDB — spatial aggregation with a CPU reference.** Replay known longitude/latitude points into a polygon aggregation with boundary cases. Validate per-zone totals against a reference with the same boundary rule, then repeat after process restart. Run the GPU cell only with supported exposed hardware and report CPU-only results separately. [HeavyDB engine and supported builds](https://github.com/heavyai/heavydb)

## Analytical processes and local storage

- [ ] **CedarDB — interrupted backup under update contention.** Use the existing witnessed mutable order corpus. Interrupt an online backup after it starts, preserve the partial artifact, and restore the previous complete backup to fresh storage. Compare the recovered snapshot to its receipt boundary while retaining the original live source. [Existing tests and follow-ups](../../cedardb/backup-recovery/README.md#future-work--todo)
- [ ] **Rayforce and DuckDB — publication of snapshots.** Work on independent copies of each engine's trade corpus. Terminate the writer at a known snapshot publication boundary and reopen from the documented available artifacts. Diff every recovered trade against the appropriate journal/transaction boundary, including missing or ambiguous tails. Preserve the existing integrity failures. [Existing evidence](../../rayforce/duckdb-comparison/README.md#future-work--todo)
- [ ] **ZFS and DuckDB/ZFS — archive restore versus client recovery.** For ZFS, receive an archived send stream into a new pool and verify dataset contents while the original is offline. Separately, interrupt a DuckDB client commit over Quack, bound the caller's wait and reconcile the ambiguous write after reconnect against the external witness. [Storage tests](../../zfs/storage-lab/README.md#future-work--todo) · [DuckDB tests](../../duckdb/zfs-recovery/README.md#future-work--todo)
- [ ] **Tableau Hyper — transactional extract refresh.** Pick the current vendor-supplied Linux artifact for the container architecture. Append a daily delta to a versioned extract, interrupt a transaction and reopen the file from a fresh Hyper process. Compare orders and grouped sums against the original fixture and a DuckDB extract. [HyperProcess](https://tableau.github.io/hyper-db/docs/hyper-api/hyper_process/) · [Published wheels](https://pypi.org/project/tableauhyperapi/)
- [ ] **Polars and Apache DataFusion — Parquet pruning.** Run lazy scans of identical partitioned files with a selective predicate and a full aggregation, using DuckDB as a third executor. Check selected IDs and integer totals, inspect plans and bytes read. Remove a referenced file on a disposable copy and require observable failure on queries that need it. [Polars lazy execution](https://docs.pola.rs/user-guide/lazy/using/) · [DataFusion CLI](https://datafusion.apache.org/user-guide/cli/index.html)
- [ ] **MonetDB — mutable column-store and hot backup.** Load a local server with the same orders as DuckDB, take a hot backup during a stream of transactional corrections and restore to a fresh database. Establish the recovered commit boundary from transaction receipts and compare full historical scans before and after restart. [Hot backup and restore](https://www.monetdb.org/documentation-Mar2025/admin-guide/backup-upgrade/hot-backup/)

## Wide-column stores

- [ ] **Apache Cassandra — wide time buckets and repair.** Compare RF3 Cassandra with the existing ScyllaDB cluster at matched consistency levels on time-bucketed device rows. Hold a replica offline during updates and deletes, rejoin and repair within the declared tombstone retention window. Inspect per-replica contents and verify exact latest values including deletions. [Anti-entropy repair](https://cassandra.apache.org/doc/latest/cassandra/managing/operating/repair.html) · [ScyllaDB baseline](../../scylladb/)
- [ ] **Apache HBase — region movement under wide-row scans.** Run HBase with replicated HDFS and ZooKeeper. Update multiple columns of a single device row atomically, split its key range and interrupt the serving RegionServer. Reopen scans at a defined boundary, reconcile complete versions per row and verify WAL replay and region reassignment. [HBase reference guide](https://hbase.apache.org/book.html)
- [ ] **Apache Kudu with Impala — late corrections at a known snapshot.** Partition readings by device and time, then correct historical readings while Impala scans Kudu. Pin the read mode and establish a snapshot or quiescent boundary for comparisons. Replace a tablet leader and verify tablets, latest bodies and sum of corrected readings. [Kudu administration](https://kudu.apache.org/docs/administration.html) · [Impala Kudu read modes](https://impala.apache.org/docs/build/html/topics/impala_kudu_read_mode.html)
- [ ] **Apache Accumulo — cell-level permissions through tablet recovery.** Add this missing wide-column case. Write a labelled incident timeline, scan as users with different authorizations and compare each exact visible cell set against an independent label evaluator. Compact and move a tablet, then repeat the checks. Revocation and recovery must preserve both confidentiality and completeness. [Cell authorizations](https://accumulo.apache.org/docs/4.x/security/authorizations) · [Compaction](https://accumulo.apache.org/docs/2.x/administration/compaction)
