# Tarantool — vshard cluster, scale out 2 → 3 → 2 replicasets

Tarantool's write scale-out path: [vshard](https://github.com/tarantool/vshard) through the
Tarantool 3 `sharding` config. Storage replicasets of 2 instances plus one router on Docker
Compose; `make scale-out` adds a third replicaset under load and the rebalancer moves 1,000 of
the 3,000 buckets to it; `make scale-in` drains it (`weight: 0`) and removes it, also under load.

## Quick start

```bash
make up         # build the image (tarantool + vshard), 2 replicasets + router, wait for bootstrap
make test       # 10,000 puts through the router, read back, bucket distribution
make scale-out  # under load: start storage-c, add it to the config, reload, wait for 1000/1000/1000
make scale-in   # under load: weight 0 for storage-c, wait until it has 0 buckets, remove it
make status     # containers; per replicaset: active/sending/receiving buckets, rows
make cli        # tt connect to the router
make down       # remove containers, volumes, the built image and the generated config
```

## Setup

| service | role | in `make up` |
|---|---|---|
| `storage-a-001` (leader), `storage-a-002` | replicaset `storage-a` | yes |
| `storage-b-001` (leader), `storage-b-002` | replicaset `storage-b` | yes |
| `storage-c-001` (leader), `storage-c-002` | replicaset `storage-c` (profile `scale`) | no; `make scale-out` |
| `router-a-001` | vshard router, `127.0.0.1:3321` | yes |
| `client` (profile `tools`) | `scripts/smoke.lua`, `scripts/load.lua` | – |

At most 7 Tarantool containers (3 x 2 storages + router).

- Image `tarantool-vshard:local` ([`Dockerfile`](Dockerfile)): `tarantool/tarantool:3.8.1` plus
  vshard 0.1.42 copied from the release tarball (the official image does not ship vshard, and
  `tt rocks install vshard` fails with `Error: 'git' program not found`).
- `app/config.yaml` is generated by [`scripts/config.sh`](scripts/config.sh) (`a b`, `a b c`,
  `a b c=0`) and bind-mounted into every container; `make` rewrites it and runs
  `require('config'):reload()` on every running instance.
- Config: `sharding.bucket_count: 3000`, storage replicasets with `replication.failover: manual`
  and a fixed `leader`, `sharding.weight` per replicaset, `memtx.memory` 512 MiB per instance.
  Users: `replicator` (replication), `storage` (role `sharding`, plus `execute` on
  `vshard.storage.info`, `kv_len`, `kv_missing`, which the router's helpers call directly),
  `app` / `secret`.
- [`app/storage.lua`](app/storage.lua): space `kv {id, bucket_id, value}` with a `bucket_id`
  index (vshard moves data bucket by bucket through it); `kv_put`, `kv_get`.
- [`app/router.lua`](app/router.lua): `vshard.router.bootstrap()` once all storages answer;
  `put(id, value)` / `get(id)` map `id` → `bucket_id_mpcrc32` → `callrw` / `callro`; `buckets()`,
  `settled()`, `check(ids)` (counts ids missing where their bucket lives, by `callrw` per bucket).

## Scaling

[`scripts/load.lua`](scripts/load.lua): 16 fibers, each `put` (unique id) then `get` (a recent
id) through the router for 60 s, retrying a failed put with the same id. At the end every
acknowledged id is checked on the replicaset that owns its bucket. Scaling starts 10 s into the
load.

2026-10-04, Apple M4 Pro, Docker VM aarch64, no CPU caps, fresh cluster (`make down up test`),
then `scale-out`, then `scale-in`, one run each:

| step | command | rebalancing | put/s before (t=1–10 s) | put/s during | failed requests | acknowledged puts lost | rows after |
|---|---|---|---:|---:|---:|---:|---|
| 2 → 3 replicasets | `make scale-out` (start storage-c, config `a b c`, reload) | 1,000 buckets to storage-c in 51.8 s | 18.5k–19.0k | 14.6k–20.8k, mostly 18.3k–19.4k | 0 | 0 of 1,115,325 | 1000 / 1000 / 1000 buckets |
| 3 → 2 replicasets | `make scale-in` (config `a b c=0`, reload, wait, stop storage-c, config `a b`, reload) | storage-c drained (1,000 buckets) in 103.5 s | 17.9k–20.2k | 15.7k–20.2k, mostly 18.5k–19.5k | 0 | 0 of 1,141,368 | 1500 / 1500, 1,132,962 + 1,133,731 rows |

- Throughput did not change with 2 or 3 replicasets: 16 client fibers through one router, each
  waiting for its put and get, are the limit here, not the storages.
- The short dips (to 14.6k–15.8k) were at the config reloads.
- Rows after scale-in = 10,000 (`make test`) + 1,115,325 + 1,141,368; nothing lost or doubled.
- Draining storage-c (~380k rows) took 103.5 s, twice as long as filling it; not investigated.
- The load ended before the scale-in drain finished, so there is no "after" figure for it.

## Known issues

- **`check()` raced with bucket moves.** The first version sent each id list straight to the
  replicaset from `vshard.router.route()` while buckets were moving and reported 6,538 "lost"
  puts after a scale-out, though the row count over all replicasets matched the acknowledged
  puts exactly. `callrw(bucket_id, …)` pins the bucket for the call; with it, 0 missing.
- **Right after a replicaset is removed**, router calls for buckets it held briefly failed with
  `NO_CONNECTION … getaddrinfo: Name or service not known` until the router re-discovered the
  buckets. `check()` retries; the load's puts never hit it (0 failed).
- **memtx full.** With `memtx.memory` at 128 MiB and ~2.77M rows from earlier runs, a third
  scale-out failed every put with `Failed to allocate N bytes in slab allocator for memtx_tuple`
  (18,038 retried attempts in 50 s) and the rebalancer logged `Error during rebalancer routes
  applying: receiver storage-c, error {"errno":12,…}`. Raised to 512 MiB.
- **The `storage` user cannot call your functions directly**: role `sharding` grants vshard's
  internal functions only; `rs:callrw('kv_len')` failed with `Execute access to function
  'kv_len' is denied for user 'storage'` until the config granted `lua_call` on it.
- Storage replicasets use `failover: manual`; on a dead master someone must change `leader`.
  Tarantool 3 also supports `failover: election` per replicaset (see
  [`../docker-compose-cluster`](../docker-compose-cluster)); not combined here.
- `bucket_count` is fixed for the cluster's lifetime; it limits how far it can be split.
